# Development roadmap

The product destination is the [original Spider Creator Engine vision](../VISION.md):
local-first autonomous software discovery, engineering intelligence, and creation.
The roadmap builds on functioning infrastructure and prioritizes useful applications
and reusable engineering experience. Work below is **PROPOSED** unless described
as implemented and supported by its corresponding acceptance evidence.

## Preserved foundation: v0.1

The initial package, CLI, capability contracts, task graphs, SQLite checkpoints,
local acquisition, controlled Python builder, verification/reporting, local AI
boundary, configuration, and failure records remain infrastructure. Their original
acceptance receipt is historical evidence. Existing behavior remains covered by
regression tests as the product grows.

## Current milestone: v0.2 — the Spider discovers and creates

Implemented additions connect resource discovery to a bounded creation workflow:

- Public GitHub repository/account/keyword discovery and richer local inspection,
  with pinned revisions, structured observations, source hashes, and explicit limits.
- Persistent resource-scoped memory, typed relationships, applicability comparisons,
  attributed corrections, and a navigable summary/decision/evidence trace.
- Creation of a Python application from explicitly selected callable components,
  followed by archive construction and a declared functional check.
- A CLI route preserving the original objective, acquisition/analysis evidence,
  component choices, generated source, build output, verification, and unknowns.
- Configurable installation destinations reserved for future delivery adapters.
- Optional source generation through an explicitly selected installed QASC CLI,
  with separate trust and functional verification; live-model qualification has
  its own evidence boundary.

Qualification must include a real local application demonstration, independent
expected results, negative cases, historical-memory retrieval in a new session,
package/CLI checks, regression tests, and a published evidence receipt. Network
isolation and live local-model behavior must each be reported as observed, failed,
or unverified; neither follows from unit tests or interface presence alone.

This milestone establishes one practical creation pattern. It does not establish
unrestricted autonomous planning, general project compatibility, or arbitrary
model-generated application correctness.

## Next milestone: v0.3 — evidence-guided discovery and adaptation

1. **Expand the useful resource-to-application route.** Add a bounded Git/HTTP
   acquisition adapter with pinned identities, hashes, transfer evidence, byte/time
   budgets, and interruption behavior. Qualify an independently sourced component
   and its license/attribution requirements before connecting it to a new app.
2. **Close a bounded local AI engineering cycle.** Supply relevant source interfaces,
   dependencies, and actual errors; persist a structured proposal separately from
   the validated plan. Run only supported, scoped actions, return real evidence to
   the model, and store interpretation as inference. Qualify actual Qwen behavior
   without assuming an offload layout or changing independent environments.
3. **Generate or adapt one missing component.** Introduce source-file proposals
   with explicit path/content limits and acceptance tests supplied independently
   of the generated implementation. Exercise changed source, wrong output, missing
   dependency, timeout, and partial execution cases. Keep verified reusable
   components separate from still-unverified generated material.
4. **Demonstrate memory-assisted diagnosis.** Reproduce a missing-runtime-resource
   packaging failure, preserve the original capsule, retrieve it for a later task,
   compare applicability, propose a repair, and verify the correction separately.
   Include a look-alike failure for which the historical fix does not apply.
5. **Measure equivalent outcomes.** Run a small task study recording human request,
   setup, intervention, review, correction, and maintenance effort; report machine
   duration separately. Preserve unknowns and negative human-time recovery.

Exit criteria: at least one useful application created from an independently
identified resource plus an adapted/generated component; reproducible verification
and source provenance; a correctly rejected repair mismatch; resumable task evidence;
and no model-driven expansion of capability or input authority. Claims of human
time recovered require an actual baseline and assisted measurement.

## Promotion rules

A proposal remains **PROPOSED** until implemented. Implementation does not prove
current availability; availability does not prove tested behavior. Functional
verification must name its procedure, environment, supported inputs, and evidence.
A successful build is not an installation, and a successful installer exit is not
functional proof. Historical repairs remain candidates until reevaluated.

Primary metric: **HUMAN_TIME_RECOVERED**. Current value: **UNKNOWN**. Secondary
counts are useful only with defined outcomes and attributable evidence; neither
feature count nor generated code volume is a substitute.
