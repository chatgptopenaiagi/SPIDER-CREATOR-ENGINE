# Software synthesis: callable components

SCE can construct a new Python application from selected existing components.
Each component exposes a declared `module:function` interface accepting a JSON
object. A generated thin CLI bridge passes each result into the next component.
Intermediate results must be JSON objects; the final result can be any JSON
value. The components remain separate in the original locations and in isolated
namespaces within the created application.

This implements a bounded instance of connecting components and creating the
missing interface. It does not implement general autonomous interface inference,
arbitrary source translation, or model-generated application code.

## Contract and provenance

`ComponentSpec(source, interface, source_files, required_modules=(),
resource_id=None, resource_revision=None)` describes an inspected Python resource.
No custom manifest is required for this API. As a convenience, a directory or
manifest path can instead supply `sce-component.json` with format
`sce.python-component.v1`, `interface`, `source_files` and `required_modules`.
Manifest `name` and `description` are optional descriptive fields.

Only explicitly selected files are copied. There is no repository-name allowlist
and no installation step. Required runtime data files must also be selected;
tests demonstrate an omitted resource failing functional verification and the
included resource passing. Interface definitions are inspected through Python AST
parsing without importing or executing source. Package modules require their
selected `__init__.py` files, and imports within a component must use relative
package imports. Absolute imports that assume an upstream source-root layout
need an independently reviewed adapter or source adjustment. Dependencies must
already exist in the chosen interpreter; the build adapter reports missing
declared modules. Native extensions and general wheel builds are outside this
adapter's qualified scope.

Every plan records selected file paths, sizes, SHA-256 hashes, interface, resource
identity and revision. A caller can supply stable identities and revisions from
discovery/acquisition; otherwise content-derived identities are used. Location
is separate from identity. The generated `sce-provenance.json` records these
sources and identifies the fixed bridge as generated by SCE. Its `NOT_RUN`
functional status is a creation-time statement, not a substitute for the later
canonical verification record.

## Lifecycle

1. `DESCRIBE` reports the interface, effects, limits and known limitations.
2. `PREPARE` validates source trust, selected paths, callable signatures, budgets,
   a fresh destination, and a caller-supplied input/expected-output fixture. It
   generates bridge and manifest contents in memory without writing files.
3. `EXECUTE` checks that sources and prepared effects still match, captures the
   selected bytes, and creates the new application source. It never imports or
   invokes selected components. Existing destinations are never overwritten.
4. `VERIFY` checks the exact constructed file set and hashes. This verifies
   construction integrity only. Application functionality remains unverified.
5. `REPORT` returns the canonical operation record, including partial artifacts
   if interrupted after writing files.

The synthesis operation is `CREATE_NEW_APPLICATION_USING_PROJECT`. The separate
`PythonBuildAdapter` builds the newly constructed project with
`BUILD_ORIGINAL_PROJECT`, then invokes its declared acceptance fixture. That
build does not mean the upstream components' original projects were built.

Caller-supplied expected output is independent of component source and bridge
generation. A passing check establishes only that declared fixture. A wrong
expected output produces a failed verification even if synthesis and building
succeeded. Explicit source trust is required: neither application execution nor
ambient dependencies are sandboxed. Source/file/input budgets are bounded; OS
RAM, CPU, process-tree and network isolation are not provided by this adapter.

## Example: create a CSV reporting application

The checked-in components under `examples/components/csv_summary` and
`examples/components/summary_report` count rows, columns and distinct values,
then produce a readable report. They remain useful individually. Their fixture
is `examples/components/csv_report_request.json`.

```python
import json
from pathlib import Path
from sce.synthesis import PythonSynthesisAdapter
from sce.builders.python import PythonBuildAdapter

fixture = json.loads(Path("examples/components/csv_report_request.json").read_text())
synthesis = PythonSynthesisAdapter()
plan = synthesis.prepare(
    [Path("examples/components/csv_summary"), Path("examples/components/summary_report")],
    Path(".sce/build_workspaces/csv-report"),
    name="csv-report", input_data=fixture["input"],
    expected_output=fixture["expected_output"], trusted=True,
)
record = synthesis.verify(plan, synthesis.execute(plan))
assert record.outcome.value == "succeeded" and record.verification.value == "passed"
builder = PythonBuildAdapter()
build_plan = builder.prepare(plan.workspace, Path(".sce/artifact_storage/csv-report"), trusted=True)
build_record = builder.verify(build_plan, builder.execute(build_plan))
assert build_record.verification.value == "passed"
```

The resulting `.pyz` accepts a JSON object from standard input, or
`--input-json '{"csv_text":"name\nAda\n"}'` for a direct invocation. Python is
required to run the artifact. Construction and building do not create an
installer or install the application.
